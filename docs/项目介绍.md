# 店小约（Shop Booking Agent）项目介绍

> 文档状态：2026-09-25。本文描述当前已实现的正式源码。技术细节见同目录《代码技术架构.md》。

## 1. 项目定位

店小约是面向**到店服务类小微商家**的 AI 预约客服助手。顾客在对话中用大白话说明需求，智能体自主调用档期查询、锁座、改期、转人工等工具，把咨询直接变成一笔写进系统的预约；老板在后台看到的是接住率、转化率和一条条结构化订单，而不是一堆散落的聊天记录。

一句话概括：**它不是聊天机器人，是一个会帮你锁座的店员。**

系统只负责预约承接与信息记录，不处理支付、不作任何医疗或法律建议。

三类角色：

- **顾客**：发起对话、锁座、确认/改期/取消，查看"我的预约"；
- **店员**：处理今日预约、到店核销、接手转人工工单并直接回复顾客（消息直达顾客对话窗，AI 不抢答）；
- **老板/店长**：配置营业时间与服务项、看板数据、维护 FAQ 知识库、处理工单。

## 2. 目标客户与需求

### 2.1 谁会为它买单

餐饮（包间/大厅）、美业（美甲美发美容）、家政保洁、教培试听、宠物服务、维修上门、健身房私教——**所有"顾客要到店、要占一个时段"的小微商家**。共同特征是：咨询高度重复、夜间和节假日无人值守、预约靠人肉记录。

### 2.2 他们到底痛在哪

这些都是公开报道中反复出现的行业原话，不是我们想象的需求：

| 痛点 | 真实场景 |
| --- | --- |
| **深夜漏单** | 晚上 9 点后微信没人回，第二天早上一看，一晚上漏了七八个预约，还有几个直接去别家订了 |
| **决策窗口只有 30 秒** | 顾客问"还有位吗"，30 秒内没人回就转头找同行；流量花钱买来了，最后死在承接环节 |
| **超卖事故** | 微信上答应了客户，但系统里忘了锁座，客户到店白跑一趟，信任直接崩掉 |
| **员工离职客户就丢** | 预约、报价、售后承诺全在店员私人微信里，人一走店里查不到，顾客重复说明需求 |
| **高峰期接不过来** | 周末几十个人同时问同一个问题，一个人同时回 5 个已是极限，剩下的等着等着就去了别家 |

### 2.3 为什么现成方案解决不了

- **大厂定制方案**：起步 30-50 万，还要年费，小微商家年营收也就几百万到几千万，投不起；
- **通用 SaaS 模板**：几千块一年但功能固定、不能改、数据在别人手里，用半年发现不合身，换又换不掉；
- **自己招人**：AI 工程师年薪 30-50 万，还配齐产品、前后端、运维，小微企业养不起；
- **招客服**：月薪几千上万，还要培训管理轮班，且**晚上不在线、节假日不值守**——恰恰漏单都发生在这些时段。

行业数据显示，2026 年一季度小微经营者净利润率均值仅 **4.4%**，**58.5% 曾因价格原因放弃或停续 AI 工具**。所以小公司买的从来不是"先进"，是**便宜、能改、马上能用**。这是本项目的第一设计约束。

## 3. 为什么这件事"必须"是智能体

这是整个项目最该讲清楚的一点。换成一次性表单或关键词机器人行不行？不行：

1. **信息必须一轮轮问出来**——"8 个人、七点、包间、有人过生日"，顾客不会一次性填完，也不该让他填；
2. **答案依赖实时状态**——"明天还有包间吗"的答案每分钟都在变，模型不能靠记忆，必须**真的去查**；
3. **要产生真实后果**——说完"帮您留了 15 分钟"，数据库里那个时段就得真的被锁住，否则就是超卖。

**反过来说：如果这三件事都不成立，就不该用 Agent。** 能说清楚"什么时候不该用 Agent"，是比"什么都用 Agent"更成熟的判断。

## 4. 主要功能

**面向老板（零代码配置）**

| 功能 | 说明 |
| --- | --- |
| 4 步开店向导 | 填店铺信息、营业时间、服务项目，点确认即自动生成 30 天档期，无需录入任何数据 |
| 档期自动生成与续期 | 按营业时间推算档期，每天凌晨自动补第 31 天，老板永不操心"档期用完" |
| 档期日历改库存 | 点某天设全天休息，点某时段改容量，改前弹窗告知影响范围；已过日期自动标记"已结束"置灰，不会把昨天的档期当成还开放 |
| 行业模板 | 餐饮/美业/家政服务项模板与 FAQ 模板，勾选即用 |
| 知识库三种录入 | 模板导入、手动添加、工单一键回流，越用越准且几乎不用打字 |
| 数据导出 | 预约记录与配置快照一键导出 CSV，数据能带走 |

**面向顾客与日常运营**

| 功能 | 说明 |
| --- | --- |
| 对话式预约 | 顾客用大白话描述需求，智能体自主追问人数、时间、特殊要求，查档期后给出可选项 |
| 真实锁座 | 确认前锁座 15 分钟，锁座期间其他顾客看到该时段为已满；超时自动释放 |
| 改期与取消 | 同会话内直接"改成 7 点半"，原子释放旧时段；取消记录原因，库存实时回补 |
| 并发防超卖 | 数据库乐观锁 + 唯一索引，两人同时抢最后一间，只成功一个 |
| 幂等保护 | 弱网重试、用户连点、模型重复调用，同一参数只生效一次 |
| 三层分级应答 | 店铺事实直接答 → 知识库查到就答 → 查不到如实告知并提议留言转达，日常问题不轻易甩给人工 |
| 人工接管闭环 | 投诉等特殊情况才转人工，工单携带完整会话摘要，**顾客不用重讲一遍**；转人工后 AI 自动闭嘴，店员在工单里回复直达顾客对话窗（店家气泡），解决后 AI 恢复接待还能接上人工聊过的上下文 |
| 知识库回流 | 未接住的提问进入工单，老板一键"采纳为标准答案"写回知识库，越用越准 |
| 老板看板 | 接住率、预约转化率、未接住 TOP 问题、时段热力图 |
| 到店核销 | 店员一键标记已到店/未到，未到计入爽约统计 |
| 多角色权限 | 顾客只看自己的，店员看本店，老板可配置；后端为最终边界 |

## 5. 效果示例

### 5.1 顾客端（深夜 11 点，老板早睡了）

```
顾客：明天晚上还有包间吗

AI：有的～想帮您确认几件事：
    ① 几位用餐？ ② 大概几点到？ ③ 包间还是大厅就行？

顾客：8个人，七点，要包间，有个朋友过生日

AI：（调工具：查 8 人包间明日 19:00 → 剩 2 间 → 锁定 1 间 15 分钟）
    帮您看了下，明天 19:00 的 8 人包间还有，我先给您留了 15 分钟。
    方便留个联系方式确认吗？另外要帮您备注生日吗？我们可以提前布置。

顾客：138****5678，备注一下要蛋糕

AI：✅ 预约成功
    📅 明日（9月14日）19:00 · 8人 · 包间
    🎂 已备注：朋友生日，需要蛋糕
    📍 地址：XX路XX号，门口可停车
    ⏰ 明天下午会再发一条提醒给您
    需要改时间，直接回这条消息就行～
```

**注意三个设计点**：档期是先查后答的，不是模型编的；**锁座 15 分钟**既防超卖也制造紧迫感；所有信息一次性写进系统——老板第二天醒来看到的是一条结构化订单，不是一段聊天记录。这直接解决了"员工离职客户就丢"。

### 5.2 改期与取消

```
顾客：改成 7 点半吧
AI：（查 19:30 → 空 → 改期 → 原子释放 19:00）
    改好了～9月14日 19:30，8人包间，生日蛋糕备注保留。原 19:00 已释放给其他客人。

顾客：算了，取消了
AI：（取消 → 释放时段 → 记原因）已取消，库存已释放。需要帮您约别的时间吗？
```

### 5.3 答不了的时候（决定老板敢不敢用）

```
顾客：你们老板在吗，上次那个事我想当面说

AI：这个我帮不上，已经转给店长了，他明天一早联系您。
    （您之前的预约记录我一并发给他了，不用再讲一遍）
```

**绝不硬编一个答案**——这条底线来自同一条工程原则：事实只能来自知识库和系统状态，模型只组织语言。

### 5.4 老板后台

```
┌─────────────────────────────────────────────────┐
│ 今日概览   9月13日                               │
│   咨询 47 条   AI 自动接住 41 条 (87%)           │
│   转成预约 23 单    转人工 6 条    漏单 0        │
│ ⚠ 本月未接住转人工：6 条（点击查看）              │
├─────────────────────────────────────────────────┤
│ 今日预约                                         │
│ 11:30  张先生  2人  大厅    已到店               │
│ 12:00  李女士  4人  包间2   已确认               │
│ 19:00  王先生  8人  包间1   🎂生日  待确认       │
│ 待处理                                           │
│ 🔴 22:15 顾客问"能不能带狗" → AI 不确定，待回答  │
│ 🔴 19:00 王先生预约未确认，已提醒 1 次           │
└─────────────────────────────────────────────────┘
```

每一条"未接住"都能点开看原文，老板补一句标准答案就回流进知识库。**这就是闭环，也是产品能越用越准的原因。**

## 6. 技术架构

| 层级 | 实现 |
| --- | --- |
| 前端 | React 18、React Router（HashRouter）、Vite、原生 fetch、手写 CSS（无 UI 框架、无图表库） |
| 后端 | Java 17、Spring Boot 3.3.5、Spring Security |
| 数据访问 | MyBatis-Plus；看板聚合用 Mapper XML |
| 数据库 | 一个 MySQL 8.0 数据库：`shop_booking`（10 张表） |
| 缓存 | Redis（可选）：对话记忆、幂等键、锁座事件、限流、JWT 注销 |
| AI | DeepSeek Chat Completions API，使用原生 `tools[]` 的 Function Calling |
| 认证 | BCrypt 密码哈希、JJWT HS256、无状态 Spring Security |
| 智能体实现 | 自研 Function Calling 循环，**代码由 AI 编程工具辅助生成**；不引入 Coze / Dify 等第三方智能体平台 |

```text
React / Vite :5173
        |
        | /api
        v
Spring Boot :8080
  |       |       |
  |       |       +-- DeepSeek API（tool_calls）
  |       +---------- Redis
  +------------------ MySQL shop_booking
```

Redis 不是业务数据库。清空 Redis 不会丢失用户、预约或档期；MySQL 是唯一业务数据源，Redis 不可用时系统自动降级照常运行。

### 6.1 为什么不用 Coze / Dify 这类智能体平台

一句话：**它们擅长编排对话，本项目卡在事务正确性。**

像 Coze、Dify 这类平台，拖拖拽拽就能搭出一个能聊天的机器人，知识库和多渠道发布也是现成的，做纯问答非常划算。但本项目要的是"说完'帮您留了 15 分钟'，数据库里那个时段真的被锁住"——这涉及事务原子性、并发防超卖、幂等和超时释放，平台给不了，最后还是得自己写代码，只是外面多套了一层壳。

另外一个现实原因：小微商家最在意的恰恰是"我的客户资料在谁手里"（这也是他们拒绝现成 SaaS 的头号理由）。既然承诺了数据自主，就不能同时把对话交给第三方平台。

**判断标准**：Agent 只会说话 → 用平台；Agent 要动手改数据 → 自己写。完整的工具对比见《代码技术架构.md》第 13 节。

代码本身不要求从零手写——循环、工具、事务的实现由 AI 编程工具辅助生成，开发者的核心工作是**设计工具契约、定失败处理规则、审查生成结果，并能用自己的话讲清每一段在做什么**。

## 7. 三分钟开店：零代码配置

> 目标用户是"只会用微信的餐饮老板"。**他不接触 SQL、不接触代码、不接触配置文件。**

### 7.1 老板实际要做的事

第一次登录后是一个 4 步向导，全程点选，约 3 分钟：

```
第 1 步  店铺信息    名称 / 地址 / 电话
第 2 步  营业时间    周一到周日各一行，时间选择器 + "休息"开关
第 3 步  服务项目    选行业模板（餐饮/美业/家政）自动带出，改改名字和价格
第 4 步  确认开店    右侧预览"将自动生成未来 30 天档期" → 点确认
```

**档期不是老板填的，是系统算的。** 老板只需说"我 10 点到 22 点营业，60 分钟一个时段，有 4 种桌型"，系统自动生成几千条档期记录，之后每天凌晨自动补上第 31 天——老板永远不用操心"档期用完了"。

### 7.2 随时改，改错的代价接近零

| 老板想做什么 | 怎么操作 |
| --- | --- |
| 明天临时不营业 | 档期日历点那天 → 选"全天休息" |
| 某天加两桌 | 点该时段 → 改个数字 |
| 改营业时间 | 设置页改 → 保存 |
| 加个新服务（露台位） | 服务项页新增 → 自动生成档期 |
| 让 AI 会答新问题 | 知识库页加一条，或从工单页点「设为标准答案」 |

**任何影响已有预约的操作，都会先弹窗告诉老板"将影响 N 条预约"，确认后才执行。** 已有预约永远不会被静默删除——这是老板最怕的事，也是最容易被忽略的设计细节。

### 7.3 知识库：三种录入方式，都几乎不用打字

1. **模板导入**：按行业预置常见问题（停车、能否带宠物、有无 WiFi、能否开发票、包间最低消费……），**勾选即入库**；
2. **手动添加**：问题 + 答案两个框；
3. **工单回流（最省力）**：AI 没答上来的问题进工单，老板答过一次，点「设为标准答案」就自动入库，下次 AI 就会了。

**用得越久 AI 越准，但老板几乎不需要额外输入**——这个闭环让产品的价值随时间增长，而不是衰减。

### 7.4 数据能带走

设置页一键导出预约记录、顾客联系方式（脱敏可选）、配置快照为 CSV。老板最怕"数据锁死"，这既是数据自主的兑现，也降低了他试用新工具的心理门槛。

## 8. 数据库

| 表 | 用途 |
| --- | --- |
| `users` | 用户、BCrypt 密码哈希和角色（customer/staff/owner） |
| `shops` | 店铺配置（按星期的营业时段、时段粒度、地址、是否完成开店向导） |
| `service_items` | 服务/桌型（包间、大厅、美甲、保洁），容量、时长、价格、取消政策 |
| `time_slots` | 档期库存，带 `capacity`/`booked_count`/`version`，并发控制的落点 |
| `bookings` | 预约单（锁座中/已确认/已取消/已到店/爽约），备注与来源 |
| `conversations` / `chat_messages` | 会话与消息流水 |
| `agent_steps` | Agent 轨迹（每轮调了什么工具、返回什么、耗时），排障时可查库追溯，不对顾客界面展示 |
| `knowledge_items` | 店铺 FAQ，含"未接住回流"来源标记 |
| `escalations` | 转人工工单 |

**只有开发者在首次部署时执行一次建表脚本**（`database/sql/01_schema.sql`，只建空表、不含任何业务数据）。此后的店铺信息、营业时间、服务项、档期、FAQ、账号全部由前端页面产生并写库，老板全程不接触 SQL。Spring Boot 自动初始化已关闭，不会在启动时建库建表。

## 9. API

| 路径 | 访问权限 | 作用 |
| --- | --- | --- |
| `GET /api/health`、`/health/ready` | 公开 | 存活与就绪检查 |
| `POST /api/auth/register`、`/login` | 公开 | 注册（选 customer 或 staff）、登录签发 JWT |
| `POST /api/auth/logout`、`GET /api/auth/me` | 登录 | 注销、当前用户 |
| `POST /api/chat` | 公开（限流） | 顾客对话，返回回复 + 会话 ID + 本轮轨迹 |
| `/api/conversations/**` | 登录且本店 | 会话、消息、Agent 轨迹回放 |
| `/api/bookings/**` | 顾客本人 / 店员店长本店 | 确认、改期、取消、到店核销 |
| `/api/slots/**` | 店员只读、老板可配 | 档期查询与临时关闭 |
| `/api/shop/**`、`/api/service-items/**` | 老板 | 店铺与服务项配置 |
| `GET /api/dashboard` | 店员（部分）/ 老板 | 接住率、转化率、未接住 TOP |
| `/api/escalations/**` | 店员 + 老板 | 工单处理与知识回流 |
| `/api/setup/**` | 老板 | 开店向导：分步保存、生成预览、完成开店 |
| `/api/knowledge/**` | 老板（店员有建议权） | FAQ 增删改、上下架、行业模板批量导入 |
| `/api/export/**` | 老板 | 预约记录与配置快照导出 CSV |

错误响应统一为 `{ "error": "错误信息" }`，便于前端直接展示。

## 11. 配置与运行

Java 配置通过环境变量提供，示例见 `backend-java/.env.example`。主要配置包括 MySQL、Redis、JWT 密钥和 DeepSeek 密钥，**真实密码与密钥不得提交到仓库**。

一键启动脚本读取 `.env`、按需构建并启动 Java 8080 与 React 5173，通过 `/api/health/ready` 等待就绪后自动打开浏览器。

DeepSeek 密钥未配置时系统仍可启动，但对话降级为 FAQ 关键词匹配 + 转人工，不会白屏或编造答案。

## 12. 数据与隐私边界

- 顾客手机号在日志与看板中一律脱敏展示，明文仅存预约表且受权限保护。
- 对话内容会发送给 DeepSeek，正式使用前必须明确告知顾客、确定保留期（默认 90 天）与删除规则。
- 发送给模型的内容只含必要上下文（店铺事实 + 本轮问题 + 工具结果），**不含其他顾客数据**。
- 档期与价格等事实只能来自数据库，模型不得自行编造；知识库没有的问题按三层分级如实告知并提议留言转达，仅投诉等特定情形才转人工。
- 审计日志只写操作类型、目标和脱敏摘要，不写完整消息正文。
- 顾客消息一律标记为数据而非指令，写工具入参在服务端二次校验，防 Prompt 注入。
